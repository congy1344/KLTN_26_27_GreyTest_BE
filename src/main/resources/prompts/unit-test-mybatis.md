# Relevant policy: mybatis
- Distinguish the service and mapper layers in MyBatis-Plus. IService/ServiceImpl methods such as save/updateById/removeById expose service outcomes; BaseMapper.insert/updateById/deleteById expose affected-row counts. Do not transfer a boolean service return to mapper.thenReturn(true): for an int/Integer mapper method use a row count such as 1/0 matching the approved setup, while keeping the approved boolean service assertion. Inspect any project-defined mapper overload before choosing its contract.
- A ServiceImpl<Mapper, Entity> inherits its baseMapper, and @InjectMocks does not fill it: stubbing a @Mock Mapper without wiring it fails with NullPointerException on getBaseMapper(). Whenever the real path reaches an inherited persistence call, put ReflectionTestUtils.setField(sut, "baseMapper", mapper) in Arrange of that test, including when the call is reached through a helper or another public method, or use an initialized spy and doReturn(...) on the reached inherited persistence boundary if the approved test allows that boundary to be isolated. Do not invent a setBaseMapper API. Never stub the actual method under test.
- For inherited list/page/getById/update/remove operations, choose ONE setup strategy per case: wire and stub the actual mapper, or stub a supported inherited boundary on a real spy. Do not leave getBaseMapper() null, stub one mapper while production reads another, or execute real database/SQL-session code accidentally. Stub exact confirmed API return types. An int/Integer row count is not boolean; a Page result is not an entity/list; preserve actual generics.
- When isolating page(...) on a spy, production may construct a new Page instance internally. Use a typed Page/IPage matcher and ArgumentCaptor to assert approved page number/size; do not match the unrelated Arrange Page instance by equality/identity. QueryWrapper and lambda wrappers may be constructed more than once; use typed matchers and inspect approved observable conditions rather than adding wrapper identity assertions.
- LambdaQueryWrapper evaluation and some ServiceImpl deletion paths require entity TableInfo metadata even without a database. If the approved scenario executes those real paths and the confirmed version/build supplies the APIs, initialize TableInfo in setup for the actual entity via com.baomidou.mybatisplus.core.metadata.TableInfoHelper.initTableInfo(new org.apache.ibatis.builder.MapperBuilderAssistant(new com.baomidou.mybatisplus.core.MybatisConfiguration(), "test"), Entity.class). This prepares framework metadata only, not a Spring context/database. A spy does not avoid this for lambda wrappers: source runs wrapper.lambda().eq(...)/orderByDesc(Entity::getter) BEFORE the inherited call you stubbed, so initialize TableInfo for that entity whenever the reached source builds a lambda wrapper, with or without a spy. Isolating the boundary on a spy is enough only when no lambda wrapper runs. Never change the business input or stub private/target business behavior to avoid metadata errors.
- Keep superclass metadata/dependency signatures authoritative to the detected build. If a version-specific API cannot be confirmed, report the precise missing technical evidence instead of inventing constructors/setters/dependency upgrades. No changes to the project's POM, business code or approved oracle are allowed.
- In particular, mocking BaseMapper.deleteById is not sufficient setup for a real ServiceImpl.removeById call: ServiceImpl can inspect TableInfo.isWithLogicDelete BEFORE invoking that mapper mock. Initialize the exact entity's TableInfo before this real path, or isolate the approved inherited removeById boundary on an initialized spy outside the target. The same metadata requirement can apply when evaluating lambda query SQL; choose fixtures for the actual reached framework path rather than assuming all framework code is mocked.
