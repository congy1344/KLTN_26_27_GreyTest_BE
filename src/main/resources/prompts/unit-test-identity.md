# Relevant policy: identity
- Preserve a fixed approved ID even when a domain constructor generates a UUID: use a verified ID constructor/setter or a mock getter returning that exact approved ID when the scenario allows a mock. Do not replace an input such as "user-1" with a random UUID and then rewrite dependency arguments to `user.getId()`; generated IDs are allowed only when the approved input permits them.
- IDENTITY FIXTURES: inspect which fields each constructor/update method assigns. An update of username/email/password does not establish an ID unless its body assigns that ID. If the case requires a fixed ID and source supplies no setter, apply the next rule (the ReflectionTestUtils ID fixture when spring-test is present; otherwise mock the confirmed domain type and stub its ID getter only on branches that read it), or use a real object's existing ID when a fixed value is unnecessary. Apart from the database-generated ID fixture in the next rule, never use reflection. Never assume a UUID generated by a constructor, or silently keep a null ID for an authenticated-user success case.
- NULL ID ON THE REACHED PATH (check this before choosing any fixture style): an entity whose ID is assigned only by the database (a declared ID field with no ID constructor argument or setter in source) has a null ID after `new Entity(...)`. Trace every ID read on the whole reached path, including private helpers and loops that run after the collaborator calls, and including entities nested inside fixtures a collaborator returns (the Product inside the OrderLine of a returned Order). If any reached statement calls a method on such an ID or unboxes it (`other.getProduct().getId().equals(line.getProduct().getId())`, `current.getId().equals(target.getId())`), or passes it to a collaborator you stub or verify with a concrete value, the entity must really hold that ID. When the build context includes spring-test (spring-boot-starter-test), keep the entity real and assign the ID in Arrange with `ReflectionTestUtils.setField(entity, "id", 30L)` and `import org.springframework.test.util.ReflectionTestUtils;`, using the exact declared ID field name and type, one value per entity and different values for different entities. This is the only reflective fixture allowed on a domain object and it may set only the ID field. Do not mock an entity just to supply an ID when this is available: stubbed getters the path never reads fail with UnnecessaryStubbingException. Without spring-test, mock the entity and stub its ID getter plus only the getters the path reads. Every ID passed to a collaborator (`repository.findByOwnerId(entity.getId(), ...)`) is stubbed and verified with the value the fixture really holds, never a literal such as `20L` that no fixture holds, because strict stubs fail on the mismatch. Leave an ID null only when no reached statement reads it or the approved scenario is about an unsaved entity.
