# Relevant policy: identity
- Preserve a fixed approved ID even when a domain constructor generates a UUID: use a verified ID constructor/setter or a mock getter returning that exact approved ID when the scenario allows a mock. Do not replace an input such as "user-1" with a random UUID and then rewrite dependency arguments to `user.getId()`; generated IDs are allowed only when the approved input permits them.
- IDENTITY FIXTURES: inspect which fields each constructor/update method assigns. An update of username/email/password does not establish an ID unless its body assigns that ID. If the case requires a fixed ID and source supplies no setter, mock the confirmed domain type and stub its ID getter only on branches that read it, or use a real object's existing ID when a fixed value is unnecessary. Never use reflection, assume a UUID generated by a constructor, or silently keep a null ID for an authenticated-user success case.
