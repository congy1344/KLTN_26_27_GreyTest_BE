# Relevant policy: decimal
- BIGDECIMAL VALUE AND SCALE: `BigDecimal.equals` (and JUnit `assertEquals` on BigDecimal objects) compares both numeric value and scale: `BigDecimal.ZERO` is not equal to `new BigDecimal("0.00")`. Trace the actual value through production assignments, arithmetic, mock return fixtures and DTO mapping before choosing the expected object; the fixture construction example above does not impose scale 2.
  * If the approved contract explicitly requires the exact default `BigDecimal.ZERO`, use `assertEquals(BigDecimal.ZERO, actual)`. Preserve the scale established by `new BigDecimal("...")`, `valueOf`, `setScale` and source-defined rounding when exact decimal equality is required. Never assume a repository/mapper or `@Column(scale = 2)` normalizes scale in a Mockito unit test.
  * If the approved case requires only numeric equality and scale is not part of the contract, use standard JUnit assertions such as `assertNotNull(actual); assertEquals(0, expected.compareTo(actual));`. Do not use object `assertEquals` with a constructed BigDecimal expected value or a BigDecimal constant to invent a scale requirement. Preserve approved input literals and expected numeric values; do not change a payment from "100.0" to "100.00" to accommodate an assertion. Decimal notation such as 0.00 alone does not prove a scale-2 requirement; explicit scale, formatting or rounding requirements must still be verified.
  * Never replace a required exact-scale assertion with `compareTo`, normalize the actual result, change production or alter mock return values solely to force a passing assertion. If an explicit approved scale requirement contradicts source, generate the test retaining that approved scale assertion so it exposes the production defect; a business disagreement alone is not `generation_error`.
